## 1. `AssetInterestModal` cannot write for anyone but Ezra — DEFECT

The guide's verification checklist records "Firestore security rules remain intact" as a pass.
That is actually the bug.

`assetInterest` has no rule of its own, so it falls through to the catch-all at the bottom of
`firestore.rules`:

```
match /{document=**} {
  allow read: if signedIn();
  allow write: if isAdmin();
}
```

`isAdmin()` is hardcoded to a single email. So every "I'm Interested" submission from a member or
visitor is denied — the entire commercial-lead-capture feature works only for the one admin
account. Persona A and Persona B in the testing guide will both fail against real rules; they pass
locally only if the emulator is open or the tester is signed in as that admin.

Add an explicit rule. Follow the `siteSuggestions` pattern already in the file, which is the right
shape for public submissions — validate the fields, allow create, restrict read to admins:

```
match /assetInterest/{inquiryId} {
  allow create: if request.resource.data.assetId is string
    && request.resource.data.engagementType in [
         'commercial-lease', 'co-development', 'land-trust-equity', 'site-inquiry'
       ]
    && request.resource.data.keys().hasOnly([...]);
  allow read, update, delete: if isAdmin();
}
```

**Check every other new collection for the same problem.** Whatever `PropertyWorkRosterModal`
writes to has the same fall-through unless a rule was added for it. A new collection in this
codebase is denied by default — that is a good default, but it means shipping a write feature and
shipping its rule are one task, not two.

## 2. Non-public assets are readable by every signed-in user — DEFECT, and it conflicts with a stated plan

```
match /beamAssets/{assetId} {
  allow read: if signedIn() || resource.data.publicVisible == true;
```

The `||` means any signed-in user reads **every** asset, `publicVisible: false` included. The flag
only widens access to anonymous visitors; it never restricts anything.

This directly breaks the plan in `RECORDING_THROUGH_GROUNDS.md`. The Georgia barn was to be entered
as a non-public asset because Ezra is deliberately not raising it with Kathy Smith until after the
October gig. Under these rules, entering it makes it visible to any signed-in user of any BEAM site
sharing this Firebase project.

If `publicVisible` is meant to gate anything, the rule needs to be:

```
allow read: if resource.data.publicVisible == true || isAdmin();
```

…with a deliberate decision about whether signed-in participants should see the non-public
pipeline. They probably should see *some* of it — but "some" needs a field, not an `||`.

Related, lower severity: `allow create: if signedIn()` lets any signed-in user inject an asset,
including fabricated `estimatedValue` and `repairCostEstimate` figures that the UI now renders as
badges.

## 3. `redevelopmentProjects` subcollections are world-readable regardless of publication

```
match /redevelopmentProjects/{projectId} {
  allow read: if resource.data.isPublished == true;
  allow write: if signedIn();

  match /{sub=**} {
    allow read: if true;        // <- unconditional
    allow write: if signedIn();
  }
}
```

The parent is gated on `isPublished`; its children are public to the anonymous internet whatever
the parent says. Anything stored in a subcollection of an unpublished project leaks. Also `write:
if signedIn()` on both levels means any signed-in user can modify any project.

## 4. The $1 Homestead needs a legal answer before it takes another submission

This is new since the last review and it is the most consequential thing in the release. One
question decides how much work it needs, and the guide doesn't say which it is:

**(a) BEAM acquires at $1** — e.g. from a municipal $1-house program — and a participant earns
*occupancy or stewardship*. Straightforward. The property stays a BEAM asset.

**(b) BEAM transfers a deed to a participant for $1.** This is a below-market transfer of
charitable assets to a private individual, and it is the shape the IRS examines as private benefit
or an excess-benefit transaction. It is routinely done legitimately by affordable-housing nonprofits
and land trusts, but only with three things in place:

- the recipient is inside BEAM's defined charitable class;
- selection criteria are objective, written, and set *in advance* (this is also Form 1023
  Schedule H territory — grants to individuals);
- and a **resale restriction** — a ground lease or deed covenant with a resale formula — so the
  participant cannot sell at market and pocket the subsidy. Without it, BEAM is handing
  appreciation to individuals, which is exactly the finding to avoid.

The encouraging part: `Land Trust Equity Participant` is already one of the four engagement types.
That *is* the mechanism. A community land trust ground lease with a resale formula solves (b)
properly. If the answer is (b), that should become the only path a $1 transfer can take, and the UI
should reflect it rather than offering a bare "Claim $1 Homestead Site."

Flag either way: `PropertyMatcherModal` attaching a "$1 site" to a profile is now creating records
that imply a claim. Worth confirming what those records are understood to promise.

## 5. The kernel has no rule for `TRANSFER` — the one stage that most needs law

`kernel.manifest.json` routes asset stage events to divisions, and the routing is sensible: CLAIM →
law, ACCESS → forge (blocking), trackD:ACCESS → health and law (both blocking), SECURE → law
(blocking).

`TRANSFER` — the last stage in the taxonomy, and the deed-moving moment — has no rule. That is the
exact event where item 4 above becomes irreversible. It should route to law, blocking.

Two smaller notes on the manifest: `urgency` carries the values `standard`, `critical`, and
`blocking` while `blocking` is also its own boolean, so the two are conflated and a reader can't
tell which governs. And the `divisions` list includes `health` and `environment`, neither of which
has a repo in play yet — those routes currently point nowhere.
